# Architecture & Implementation: Kiosk PDF Pre-Download & Refactored Payment Flow

**Date:** March 22, 2026  
**Context:** Full system refactor to pre-download the user's PDF to the Kiosk before or during the payment process, ensuring minimal waiting time for the user after payment is confirmed.

---

## 🏗️ High-Level System Design

1. **Upload Phase:** When the user processes the PDF (merged, converted to Base64 via `UploadPage.tsx` and saved to `localStorage`), they land on `PaymentPage.tsx`. The frontend immediately triggers an S3 upload without waiting for payment. This occurs silently in the background.
2. **Kiosk Push:** Upon the frontend sending `/upload-complete`, the backend notifies the exact physical Kiosk using a WebSocket channel (`download-file-from-s3-request`), instructing the Electron app to download the pre-signed S3 URL immediately. 
3. **Information Overlay:** As the Kiosk initiates the download, it hides its native QR code completely and displays an animated "Downloading your file..." overlay until it’s finished unpacking.
4. **Unlocked Payment Gate:** The user doesn't wait for S3. They proceed to select "Pay Rs X". The backend returns a dummy success.
5. **Real-Time Polling Gate:** After payment, the user gets a "Start Printing" button. Clicking this does a real-time check. If the Kiosk isn't done downloading, it restricts the user and updates the status to "Kiosk Downloading...". If the Kiosk is done, it formally dispatches the print job logic to the Kiosk.

## 🛠️ Codebase Modifications & Implementations

### 1. Database Schema (`PrintGoAll/server/prisma/schema.prisma`)
Added crucial granular statuses to `NoAuthUser`:
- `s3UploadStatus`: ("pending", "uploaded", "failed")
- `kioskDownloadStatus`: ("pending", "requested", "downloading", "downloaded", "failed")
- `isPrintStarted`: (Boolean, defaults `false` — becomes true when user dispatches `/start-print`)
- `isPrinted`: (Boolean, defaults `false` — becomes true when Kiosk `print-file-response-to-server` acknowledges success)
- `paymentStatus`: (Tracks successful mock UPI payments)

> **Key Takeaway:** The separation of `paymentStatus`, `isPrintStarted`, and `isPrinted` mathematically guarantees safe and flawless Refund API triggers in the future (e.g. `paymentStatus == 'success'` but `isPrinted == false`).

### 2. Backend API APIs (`PrintGoAll/server/src/modules/upload/upload.routes.js`)
* **`/upload-url`**: Generates a 600s S3 Upload URL and creates the initial `NoAuthUser` record with statuses set to "pending".
* **`/upload-complete`**: Patches `NoAuthUser` to S3 Uploaded and shoots a WebSocket event (`requestKioskS3Download`) to the physical print Kiosk ID in the background.
* **`/download-status`**: New GET API strictly built for the React frontend to poll over HTTP every 3 seconds to check on the real-time sync of the Prisma database records. Also returns boolean fields `isPrintStarted` and `isPrinted`.
* **`/start-print`**: Verifies `paymentConfirmed` and updates Prisma's `printStatus: "printing"`, `isPrintStarted: true` while dispatching the print instructions. 

### 3. Backend Sockets (`PrintGoAll/server/src/ws/handlers/kiosk.handler.js`)
* Handled incoming acknowledgments of `download-file-from-s3-ack`. Updates the `kioskDownloadStatus` directly to `"downloaded"`.
* Handled incoming acknowledgments for `print-file-response-to-server` & `printed-status`. Directly updates the `isPrinted` database flag to true. 

### 4. React Frontend (`PrintGoAll/printgoapp/src/pages/PaymentPage.tsx`)
Re-engineered the UI flow to correctly handle caching failures and React strict mode unmount bugs:
- Implemented a `useRef(false)` system (specifically `uploadStartedRun`) to fix a severe bug in React 18 
  where strict-mode double-mounting artificially triggered server-side 429 Rate Limits from `/upload-url`.
- Caches the `UPLOADED_FILE_NAME` safely via `localStorage`.
- Handled UI rendering for distinct phases:
  - `"Preparing PDF..."` → `Payment processing...` → `Pay Rs X` → `Waiting for kiosk to finish downloading PDF` → `Start Printing`.

### 5. Electron Kiosk Renderer (`PrintGoKiosk/app/src`)
* Modified `index.html` to integrate a fully animated visual downloading layer consisting of a rotating gear & progress slider over a frosted-glass UI.
* Wired `ipcRenderer` commands (`main/socket.js` -> `renderer/renderer.js`) to parse `show-downloading` and `hide-downloading` events. The Electron main process intercepts the websocket download command, shows the downloading animation, extracts the data from S3, verifies binary integrity, hides the animation, and returns the formal acknowledgment back to the PrintGoAll node server.

## 🔮 Edge-Case Resiliency & Retries
- **Stale Browser Session Refresh:** If `PaymentPage` identifies a cached `fileKey` but the backend has crashed or lost standard WebSocket states, `PaymentPage` will safely delete the stale fileKey and seamlessly repeat the full `uploadMergedPdf` logic without user intervention.
- The 2000-millisecond S3 Signed URL rate-limit logic cleanly protects our S3 bucket infrastructure from DDoSing.

## ✅ Patch Update (Appended): Payment Page Polling Fix

### Problem Observed
Even when the kiosk downloaded the file successfully (`kioskDownloadStatus: downloaded`, `isDownloaded: true` from backend logs), the Payment UI could remain stuck at **"Preparing..."** or not transition reliably to a ready state.

### Root Cause (Frontend State Lifecycle)
The issue was not in backend status persistence. The backend and kiosk events were correctly updating the database. The inconsistency was in the frontend polling/timer lifecycle and phase mapping on `PaymentPage.tsx`.

### Changes Applied (March 22, 2026)
File updated: `PrintGoAll/printgoapp/src/pages/PaymentPage.tsx`

1. Added stable polling control with `pollTimerRef`.
2. Introduced `startPolling()` and `stopPolling()` helpers to avoid duplicate/stale intervals.
3. Added unmount cleanup to always clear active polling timer.
4. Refined phase mapping in `pollDownloadStatus()`:
  - `downloaded` -> set `downloadPhase = "downloaded"` and stop polling.
  - `failed` -> set `downloadPhase = "failed"` and stop polling.
  - `requested` / `downloading` -> set `downloadPhase = "kiosk-downloading"`.
  - `s3UploadStatus = uploaded` -> set `downloadPhase = "uploaded"`.
5. Decoupled upload flow from continuous polling:
  - Upload still starts in background immediately.
  - Polling is now triggered after payment (`isPaid === true`) so payment remains non-blocking.
6. Preserved real-time guard on print click:
  - `handlePrint()` still does a final `checkDownloadStatus()` call and blocks print if not downloaded.

### Backend/Kiosk Verification (No Additional Code Needed)
Verified existing event path is correct:

1. Kiosk receives `download-file-from-s3-request` and emits `download-file-from-s3-ack` on success/failure.
2. Backend handler (`kiosk.handler.js`) processes ack and updates Prisma `kioskDownloadStatus` to `downloaded` or `failed`.
3. Frontend polling endpoint (`/userdocs/download-status`) returns `isDownloaded` and latest status fields from Prisma.

### Expected UX After This Patch
1. User can pay while kiosk is downloading.
2. After payment, status checks run every 3 seconds.
3. Once backend returns `isDownloaded: true`, UI transitions to ready and allows normal print flow.
4. If still downloading, user sees accurate waiting state instead of indefinite "Preparing...".
