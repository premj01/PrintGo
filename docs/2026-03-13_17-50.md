# PrintGo Architecture & Implementation Log
**Date:** March 13, 2026
**Session Update:** 17:50

## 1. Backend Fixes & Service Stability
- **Missing `getMe` Export:** Resolved a critical `SyntaxError` by implementing the `getMe` controller in `admin.auth.controller.js`. This allows the frontend React context to verify JWT sessions and retrieve admin profile data (username, role) on page refresh.
- **WebSocket Broadcast Refactoring:** Transitioned from a single-admin `adminState` to a global `adminSockets` collection. All machine heartbeats and job statuses are now broadcast to *every* connected admin window simultaneously.

## 2. Real-Time Data Synchronization (Telemetry)
- **Agent Auto-Discovery:** Modified `agent.handler.js` to automatically parse OS-level telemetry (hostname, arch, platform) from incoming `system-info-result` messages and update the MongoDB `machineDetails` block.
- **Printer Hardware Sync:** 
  - Integrated `printer-list-result` logic into both `kiosk.handler.js` and `agent.handler.js`. 
  - When an admin clicks "Sync Hardware," the server now intercepts the physical printer names from the kiosk and automatically maps them to the `printers.bw` and `printers.color` database records.
- **Revenue & Metrics Automation:** 
  - Implemented automatic `$inc` (increment) logic on `printed-status` success events.
  - The database now handles the summation of `totalPrintJobs` and revenue (`total`, `monthly`, `daily`) in real-time as jobs complete.

## 3. Multi-Admin Concurrency & Locking
- **Exclusive Kiosk Management:** Introduced a state-locking mechanism to prevent multiple admins from sending conflicting commands (like `Restart` or `Terminal` inputs) to the same machine.
- **Lock/Unlock Protocol:** 
  - When an admin views a specific kiosk detail page, the frontend requests a `view-kiosk` lock.
  - If already managed, other admins receive a "Management Denied" notice with the name of the admin currently in control.
  - Buttons are disabled in the UI for the non-controlling admins.
- **Lifecycle Management:** Locks are automatically released (`leave-kiosk`) when an admin navigates away or disconnects.

## 4. Flaw Inspection & Security Audit
*I have inspected the current state of the backend and frontend. Below are the identified potential flaws and recommended actions:*

### A. Admin Activation Barrier (Flaw)
- **Problem:** Newly registered admins have `isActive: false` by default. There is currently no UI for a "SuperAdmin" to activate them.
- **Risk:** New team members will be stuck at the login screen after signing up.
- **Fix:** Need an "Admin Management" page where SuperAdmins can toggle the `isActive` flag for other staff.

### B. Revenue Pricing Logic (Inconsistency)
- **Problem:** The `printed-status` event currently relies on a `price` field potentially sent from the kiosk agent. 
- **Risk:** If the agent is compromised or buggy, it could report incorrect revenue.
- **Fix:** The server should calculate the price based on the `Kiosk.printers.pricePerPage` stored in MongoDB multiplied by the known page count of the job, rather than trusting the agent's reported price.

### C. Terminal Security (Concurrency)
- **Problem:** While management is locked, the underlying PTY terminal session on the kiosk agent might still be shared if not explicitly closed.
- **Risk:** Potential "ghosting" of terminal buffers if an admin leaves the page improperly.
- **Fix:** Ensure the `terminal-closed` event is strictly enforced on `leave-kiosk` or socket timeout.

### D. CORS/URL Hardcoding (Optimization)
- **Problem:** Frontend `AdminKioskDetailPage.tsx` still has `http://localhost:3000` URLs hardcoded in several places.
- **Risk:** Will break immediately when deployed to a production staging server or a different network IP. 
- **Fix:** Move the Base URL to an `.env` variable or a centralized `api.service.ts`.
